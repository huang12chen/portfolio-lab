# 字的落地执行

[视觉方向](visual-direction.md) 负责选定阶梯、字距与中文修正。但一套设计声明可以在这些上都对、页面却仍然难看，因为让字看起来是"排出来的"而不是"摆上去的"的那些判断，全都不在阶梯里：竖着对齐的数字、按本地写法书写的数量、不被抛下的末行、与测量本身相称的精度，以及光学上笔直而非几何上齐平的边。本文件不给任何定值。

[English version](../typography-execution.md)

## 数字有两种写法，一个页面通常两种都要

读者**纵向**扫的数字需要等宽字身，好让一列的量级在竖直方向上对齐；读者**在句子里**读的数字需要落在行文节奏里，这是比例数字做得到而等宽数字做不到的（一个等宽的 `1` 夹在正文里，看起来像是被人为加了空格）。所以一张有指标表格、同时正文里又引用同一指标的句子，就是一个需要两种数字模式的页面；两种场合共用一种模式就是缺陷。

字体也要查：`font-variant-numeric: tabular-nums` 是一个请求，不是保证。字体若不含 `tnum` 特性，会接受这条声明且什么都不改，于是列仍然歪着，而 CSS 显示它已被修好。

**检查。** 对每个"文本是数字、且位于列或表格单元中"的元素，测量其中每个数字字形实际渲染出的字身宽（`0`、`1`、`8` 互相对照）；合格要求三者相等。然后找出行文里的数字，确认它们**没有**沿用表格那一套模式。再确认模式是真实存在的而不是只被声明的：若宽度不等，就是字体没有这个特性、声明只是装饰——如实写下这一句，然后换一支有这个特性的字体，或者重构这一列。

## 数字的写法属于语言，不属于字符串

一个双语站点在两种语言里都渲染 `12,800,000`，等于什么都没本地化。中文以四位为节、对齐 `万` 与 `亿`，所以同一个量是 `1280 万`；货币符号、符号与数额之间的空格、负数的处理、日期顺序与单位全都不同；百分号在表格里与在行文里的位置也不一样。同一语言内部也有缩小版的同类问题：图表标签写 `2.3k`、下面那句正文写 `2,300`，这是两句关于精度的主张，不是一个数字。

写法由数字被阅读的位置推出。位置紧张的标签用压缩形式，但绝不许丢掉单位。承担论证的数值用完整位数，并附上它是在哪一段时间上测出来的。

**检查。** 对每个在两种语言里都出现的数字或日期串，报告两处各自的渲染结果。合格要求：凡是两种语言的分组、单位或日期惯例不同之处，两处渲染必须不同；只在真正应当相同的地方相同（标识符、版本号、文件名）。然后找出同一条路由上被写成两种样子的同一个量。

## 说不出依据的位数就是编出来的位数

用一个只支持两位有效数字的来源，报出五位有效数字，是生成式页面最常用的一种撒谎方式——用排版撒，而不用文字撒。虚假精度在一个看不到电子表格的读者眼里就是权威，而这件材料的主人在面试里没法为它辩护。所以位数由测量自身的误差范围、或底层记录的粒度推出——取更粗的那个——并且第一次出现这个数字的地方就写下取整规则。

百分比有它专属的坑：从 4% 到 6%，相对增幅是 +50%，绝对差是 +2 个百分点，引用哪一个是一种主张。选定一个、写明是哪一个、并在全页保持一致。

**检查。** 对已发布文本里的每个数字，在原始材料或 `DESIGN.md` 中找到它的依据。凡有效位数超过依据支持的，一律 fail；凡百分比没有说明是相对还是绝对，一律 fail；凡数字在使用处缺少它所对应的时间段，一律 fail——见[内容与证据](content.md)，那里有同一条规则，因为它同时是一个以文字出现的缺陷。

## `balance` 是给行的，不是给段落的

`text-wrap: balance` 的存在是为了解决"两行标题的第二行只剩两个词"，它的工作方式让各行长度趋于一致。用在段落上恰好是错的：正文本该是参差的，而把各行拉平会造出一块有两个意外边缘的河状文本。用在很长的标题上，它可能把形容词和它修饰的名词拆开——那比它修掉的孤行更难读。所以规矩是作用范围，不是是否使用：标题、标签、图注与短的导语可以用；超过约三行渲染结果的块不许用；正文用 `pretty` 或者不用。

这件事比它多出的那几行 CSS 重要，是因为 balance 改变的是屏幕上最醒目那个物件的**形状**，而被平衡成沙漏形的标题是一个没有人做过的、看得见的决定。

**检查。** 对每个声明了 `text-wrap: balance` 的元素，报告它的渲染行数与最短那行的字符数。任何超过约三行的平衡块都 fail；任何最短行只有一个词（拉丁）或少于三个字符（中文）的平衡块也 fail——那是算法为几何挑的断点，而读者体验到的是错误。然后查正文：若任一段落的末行短于栏宽的四分之一，且页面没有使用 `text-wrap: pretty` 或等效手段，把它作为孤行报告出来。

## 栏边是光学的

一条左对齐的文字，如果各行开头是斜体、引号或中文全角开括号，它就与任何东西都不齐平：**墨迹**比盒子更靠里或更靠外，于是文本的边缘恰好在读者用来定位下一行的那个地方参差起来。受支持时用悬挂标点解决；不支持时给受影响的首字符一个很小的负向缩进作为替代。两者都没有的页面，等于同时有一条画出来的边和一条参差不齐的墨迹边——这正是"间距有点不对但我说不出哪里不对"通常所指的东西。

同样的道理适用于任何把几何当作居中的地方——见[空间构造](spatial-construction.md)——也适用于混排行：汉字里夹一个拉丁词需要一丝空格，而拉丁数字的高度不会与周围的汉字一致。

**检查。** 逐行测量一栏文字墨迹左边与栏盒边界的距离并报告散布；散布大于字距本身能解释的量，就是未悬挂的边。中文另外确认两件事：开首括号与全角标点不要把行首汉字推进得比其余各行更深，以及 `line-break` 要紧到不会出现 `。」` 单独占一行、而它的句子结束在上一行的情况。

## 字重要么可分辨，要么就是装饰

一个字重系统里有 400、500、550、600、650、700，读者能可靠区分的差不多只有两个，其余是设计师自己的私人词汇。与像素字号阶过多是同一个坑：更多的阶不是更强的层级，而是阶与阶之间更小的差，而低于最小可觉差的差在任何距离上都不携带信息。

所以先数清页面实际需要做的区分——通常是：正文、强调、标签、展示——再给每一个一次读者在它将被使用的那个字号下看得见的差别，并记住字重对比会随字号变小而缩小，因此元信息那一行需要比标题更大的差。

**检查。** 收集实际使用的不同 `font-weight` 值，并配上每个值出现时的字号。当层级上相邻的两个字重在两者中较小的那个字号下相差不足一个真实阶，fail；当超过四个字重被用来承载多于一种区分，fail。然后一个决定性测试：把整页渲染成单一字重，数一数还剩几种区分不被发现——没被发现的那些，本来用对比之外的手段也能承载。

## 小字是一个决定，不是一条底线

元信息、图注与标签排在阅读字号之下是有原因的：它们不是论证。但 1440 屏幕上的小字是在 60 厘米处被看的，不是手机那种 35 厘米，所以同样的名义像素尺寸只有更小的视角——一个随容器变宽而把**标签**缩小的页面，最后会是桌面上落满灰尘、手机上反而清楚，与想要的关系恰好相反。小是可以的；只在宽屏上才存在的"更小"才是结论。

截断是它的近亲：`-webkit-line-clamp` 与 `text-overflow: ellipsis` 用在主标签上是在悄悄删内容，而读者分不出一个被裁短的标题和一个本来就短的标题。

**检查。** 对每个承载文本的类，报告它在 1440 与 390 下的计算字号。任何非展示标题的类若视口变大时字号反而变小，fail；任何连续文本（不只是一个短标签）小于"在同一观看距离上页面正文仍可读的下限"，fail。然后找出每个被 clamp 或被省略号处理的元素，确认完整字符串仍然可达——`title` 属性、详情页、或源文件——并确认其中没有任何一个是某样东西唯一的命名处。

## 顺序

字的落地排在阶梯选定之后、其余一切视觉评判之前：表面、动效与图像全都是拿读者正在试图阅读的文字来被评价的，而一列里用了比例数字的表格，会被一个判断完全正确的评审报成"对不齐"，原因却被归到版式以外。修的顺序是：数字模式、然后是数值写法与精度、然后是 balance 的范围、然后是栏边、然后是字重阶。上面每条规矩同时都是[视觉验收](visual-review.md) 里的一行，而它们引用的数值要写在 `DESIGN.md` 里方向声明旁边，因为一个没有记录依据的字排决定，与一个默认值无法区分。
