# 参考研究

只听说过名字的参考，改变不了任何设计。一个站点的名字、文章里的截图、HTTP 200、它自己的宣传文案、装得顺顺当当的依赖包，这些只能证明它存在，不能证明你看懂了它。研究深度服务于一个具体的设计问题，不是无边界地爬。

[English version](../reference-research.md)

## 顺链路走到真正能拍板的那一层

| 你从哪儿开始 | 真正有价值的是什么 | 走到哪儿算够用 |
| --- | --- | --- |
| 一篇文章或资源合集 | 正文里那些实质链接，然后是具体站点 | 你能说清这条参考改了本页的哪一处，以及怎么验证改造结果 |
| 灵感站 | 分类 → 案例 → 原始站点，而不是灵感站里的缩略图 | 你按自己要做的宽度看过真实版式，并亲手试过打算借的行为 |
| 组件库 | 组件本体、预览、参数、实现与使用条件 | 你知道它的触发方式、状态、依赖、回退和改造成本 |
| 动效或特效说明 | 跑起来的 demo，不是安装命令 | 你看过进场、过程、退场、复位，以及减少动效时的路径 |
| 用户发来的一张截图 | 这一帧里看得见的东西 | 你没有声称看不见的动效、没看到的下方内容、或完整流程 |

登录页、付费墙、以及只会返回 200 的空壳，都不算案例内容。展示视频证明的是那段录屏的行为，不是你真的用过这个产品。某个来源打不开时，记下 `blocked` 和你试过哪些路，然后继续独立工作；改状态标记不是补救办法。

普通的作品集工作只需要两三条真正影响构建的参考。如果用户要求覆盖清单里的每一条，先把实质链接去重，逐条写明到达的深度和限制，排除无关导航、广告、账号与分享。不要用几条深读的结果去代表整份清单。

## 从悬而未决的问题出发，不是从收藏夹出发

被点了名的网站不是研究计划。按当前没解决的那个设计问题去挑参考，因为一个回答没人想问问题的来源，只会花掉构建时间、什么也不改。

| 还没定下来的是什么 | 去看哪里 | 到达并比较什么 |
| --- | --- | --- |
| 读者该做什么、按什么顺序 | 真实产品的界面库与流程录屏 | 某一个具体界面的目的、它需要的上下文、它的状态，以及哪些属于可选深度 |
| 这份材料想要什么构图 | 作品集与单页网站画廊，然后是你挑中那一条的原始站点 | 首屏、紧接着的下一个有信息的分区、导航，以及浏览的代价 |
| 别人的字体为什么立得住 | 字体搭配索引与字厂样张 | 一组具体搭配在真实页面里的样子、真实文案在真实字号下的表现、字符覆盖、字重与授权 |
| 这里该用哪种交互 | 组件库与动效画廊 | 触发、前后状态、归位、焦点、触屏、减少动效、依赖、降级 |
| 哪些素材是诚实的 | 图标集、插画库、摄影库 | 某一个具体家族或某一张图的构图与使用条款 |
| 各种选择怎样合成一套系统 | 品牌与设计规范文档 | 语义角色、分级色值、对比度、字阶层级，以及跨多个真实页面的组件状态 |

这些是路径，不是必须的技术栈，也不是每个项目都要重新走一遍的清单。

## 配方不是研究

特效画廊和提示词合集公开的是成品指令。读一条只能知道作者做了什么，不能知道那个机制对读者做了什么；而直接贴上去就会得到他的网站：同样的缓动、同样的骨架、同样顺序的三段内容。改为打开运行中的例子，记下触发它的是什么、哪个属性在变、它怎么归位、降级是什么，然后针对自己这份材料写一遍规格。装进来的组件默认值同理：预设带着原作者的内边距、圆角和时长，而那些属于另一个项目。

## 记下数字，不要记下印象

当你借的是行为，就把它量出来。*滚轮把页面从 0 推到 1800px，多出两行图和视频。* *悬停把图标从 50px 放大到约 70px，离开时回到 50px。* *Esc 让对话框计数从 1 变回 0。* *回车关掉了开场，并改变了音频控件。* 数字下个月还能复核，它不会因为你喜欢这个站而被美化，而且它清楚地告诉别人你到底动手试过什么。"滚动很顺滑""悬停挺舒服"描述的是一种心情，什么也没证明。

## 记下你实际到达的深度

在 `DESIGN.md` 里给每条参考标一个词，周围的句子承担观察内容：

- `discovered` —— 只知道它存在。
- `text-read` —— 读过文章或文档的相关正文。
- `visual-inspected` —— 看过运行中的页面，或它诚实的截图，且是在真实宽度下。
- `interaction-tested` —— 亲手触发过行为，观察到前、中、后，以及触屏或键盘的替代路径。
- `integrated` —— 已经实现进本项目，并在运行结果里验证过。
- `blocked` —— 拿不到，写明原因和试过的路径。

搜索结果或抓取到的页面只是检索记录，它自己不能提升上面任何一档状态。

项目证据——本人的材料、截图、参考笔记——留在该项目里。它们不该进入共享的 skill 状态，也不该进入公开示例；别人的文章和图片不会因为对你有用就变成可分发的素材。

然后写下这三段式，这才是让参考在构建之后仍然可用的东西：

- **观察** —— 这条参考在做什么，用机制说，不用形容词。*标题栏和正文栏用了不同宽度，空间是按阅读路径组织的。*
- **改造** —— 本站改成做什么。*居中的阅读栏配左对齐长文；原件按自己的比例摆放。*
- **验证** —— 怎么知道它成了。*1440 下两侧留白均衡，390 下行长仍然可用，标题依然可扫读。*

"高级""精致""有质感"这类没有依据的形容词不是观察。它们描述的是一种强度，既没法检查，也没法交接。

## 不要把证据锁在特效后面

不管借了什么，读者看到作品的通道都不能依赖那层表演成功。

- 必要内容靠普通滚动就能到达。不要把滚轮劫持成推进叙事的手段，读者本来应该能自己略读。
- 必须被看见的东西不能只在悬停时出现；触屏和键盘读者默认就要拿到同样的信息。
- 任何证据都不能只在动画的某一精确时刻出现，也不能在动画被跳过、脚本失败、素材没加载时消失。
- 共享元素过渡与跨页动效不能复制出第二份导航，也不能留下残影文字。检查固定导航、字体加载和原生返回；效果不可靠时，退回普通导航。

这些差别决定一个作品集是"技术很漂亮"还是"真的能用"，而在特效中途截一张图，完全看不出问题。
